# تقرير تقييم قالب OpenTik

**تاريخ المراجعة:** 2026-09-08  
**النطاق:** القالب المصدر، نظام البناء، القوالب، الأجزاء الجزئية، Customizer، JavaScript/CSS، التوثيق، وحالة حزمة الإصدار.  
**نوع المراجعة:** تدقيق ساكن ومراجعة بصرية للصورة المرجعية، وليس اختبارًا وظيفيًا على موقع WordPress حي.

## 1. الخلاصة التنفيذية

القالب في حالة **نسخة تجريبية متقدمة / MVP بصري** وليس في حالة إطلاق إنتاجي مكتمل. يمتلك أساسًا جيدًا وهوية بصرية واضحة، كما أن البناء المحلي سليم، لكن توجد فجوات في العقود الوظيفية، الوصولية، SEO، الخصوصية، الاختبارات، وتزامن التوثيق مع الكود.

التقدير الإجمالي التقريبي: **5.3/10**.

| المجال | التقدير | الحكم |
|---|---:|---|
| البنية الأساسية | 6/10 | مقبولة، لكنها ما زالت مرتبطة بقوالب كبيرة ومنطق عرض متكرر |
| الواجهة والهوية البصرية | 7.5/10 | مميزة ومتسقة بصريًا، مع مبالغة في المؤثرات والحالات الثابتة |
| الوصولية | 4.5/10 | توجد أساسيات جيدة، لكن التفاعل المركب غير مكتمل للوحة المفاتيح وقارئات الشاشة |
| الأداء | 5/10 | البناء مضغوط، لكن عدد الاستعلامات والخدمات الخارجية والمؤثرات يحتاج ضبطًا |
| الأمان والخصوصية | 5/10 | الهروب موجود في مواضع كثيرة، لكن التتبع والسجلات والاشتراكات تحتاج سياسة واضحة |
| SEO وصحة المحتوى | 3.5/10 | لا تظهر طبقة structured data أو canonical أو Open Graph في القالب |
| الاختبارات والتوثيق والإصدار | 3.5/10 | توثيق أولي جيد، لكن بعض ادعاءاته لا تطابق التنفيذ ولا توجد اختبارات WordPress/متصفح |

## 2. نطاق الأدلة والقيود

تمت مراجعة 20 ملف PHP مصدرًا، بإجمالي يقارب 2575 سطرًا، وملف CSS مصدرًا من 1089 سطرًا وJavaScript من 439 سطرًا. توجد 61 إعدادات Customizer و4 استعلامات `WP_Query` صريحة، إضافة إلى استعلامات التصنيفات والوسوم والصفحات.

تم التحقق من الآتي:

- `npm run build` ينجح.
- `npm run lint` ينجح.
- `npm run verify` ينجح.
- فحص صياغة PHP ينجح لكل ملفات PHP المصدرية.
- لا توجد مواصفة feature أو `plan.md` أو `tasks.md` داخل `specs/`؛ لذلك فهذا التقرير تدقيق مستقل وليس مراجعة تنفيذ مقابل مواصفة معتمدة.
- لم يتم تنفيذ اختبار متصفح، أو اختبار Lighthouse، أو تشغيل داخل WordPress فعلي؛ أي ادعاء حول زمن التحميل أو سلوك الإضافات يحتاج تحققًا لاحقًا.

## 3. الجوانب الإيجابية

### 3.1 البنية البرمجية

- وجود فصل أولي بين `inc/` و`parts/` و`assets/src/` وملفات القوالب يجعل نقطة البداية مفهومة.
- استخدام `get_template_part()` للأجزاء المتكررة جيد، خصوصًا بطاقة المقال والمشاركة والشريط الجانبي.
- `functions.php` صغير نسبيًا ويقوم بتحميل الوحدات الأساسية بدل وضع كل المنطق فيه.
- استعمال بادئة `opentik_` يقلل احتمال تعارض الأسماء مع الإضافات.
- وجود `function_exists()` في عدد من الدوال يضيف قدرًا من التوافق مع التخصيصات الخارجية.

### 3.2 توافق WordPress

- دعم `title-tag` و`post-thumbnails` وHTML5 و`automatic-feed-links` و`align-wide` و`responsive-embeds`.
- تسجيل قائمتي primary وfooter، وحجم صورة مخصص للبطاقات.
- وجود `wp_footer()` و`wp_head()`، ودعم الشعار المخصص، والتحديث الانتقائي للهوية.
- وجود نصوص قابلة للترجمة عبر text domain `opentik` في أجزاء كثيرة.

### 3.3 تجربة المستخدم والهوية

- هوية عربية RTL واضحة، مع تخطيط responsive وبطاقات وأرشيف يدعم grid/list/masonry.
- النمط الداكن والفاتح مبنيان على متغيرات CSS، وليس على نسختين كاملتين من الواجهة.
- شريط تقدم القراءة، وضع القراءة، البحث، القائمة الجانبية للجوال، مشاركة المقال، وطباعة المحتوى تعطي قيمة حقيقية للقارئ.
- الصورة المرجعية تظهر تسلسلًا بصريًا جيدًا: هوية، تنقل، عنوان قسم، وبطاقات ذات تمييز واضح.
- استخدام أحجام صور WordPress في البطاقات والشريط الجانبي أفضل من تحميل الأصل دائمًا.

### 3.4 الجودة الأولية وسير البناء

- Webpack وPostCSS وTailwind يعملون محليًا، والأصول النهائية مضغوطة.
- استخدام `filemtime()` لإصدار CSS وJavaScript يقلل مشكلة cache قديم بعد النشر.
- وجود `README.md` و`PROJECT_MAP.md` و`screenshot.png` و`verify-build.js` يوفر أساسًا مناسبًا للتوثيق والإصدار.

## 4. الجوانب السلبية والمخاطر

الأولوية: **P0** مانع إطلاق، **P1** مهم قبل الإنتاج، **P2** تحسين لاحق.

### 4.1 وظائف ذات عقد غير صحيح — P0

1. **النشرة البريدية وهمية وظيفيًا.** في `parts/sidebar-single.php:152` لا يوجد `action` أو endpoint أو حفظ للبريد، وفي `assets/src/js/main.js:160-194` تظهر رسالة نجاح بعد `setTimeout` فقط. هذا يضلل المستخدم وقد يفقد بياناته. يجب إما ربطها بخدمة/REST endpoint حقيقي مع سياسة موافقة، أو إزالة الرسالة واستبدالها برسالة واضحة بأن التكامل غير مفعّل.

2. **التوثيق يصف تدفقًا غير منفذ.** `PROJECT_MAP.md` يذكر REST API وlazy-load وstructured data وcache purge، لكن الكود الحالي يعرض Server-side rendering تقليديًا ولا يحتوي طبقة REST أو JSON-LD أو hooks للكاش. يجب اعتبار هذه البنود أهدافًا مستقبلية لا مميزات مكتملة.

3. **حزمة البناء المنفصلة غير متزامنة مع المصدر.** مجلد `build/` مستثنى من Git ويحتوي ملفات تختلف بصماتها عن ملفات المصدر، منها `inc/color-utils.php` غير موجود في المصدر. لا يوجد مسار إصدار موثوق يثبت أن ZIP الموزع ناتج عن آخر commit.

### 4.2 توافق WordPress — P0/P1

- `header.php` يفتح `<body>` دون استدعاء `wp_body_open()`. هذا يكسر نقاط إدخال الإضافات والوسوم المطلوبة لبعض أدوات التتبع والأمان.
- قالب `404.php` غير موجود، ولا توجد معالجة مخصصة للصفحات الفارغة أو الأخطاء على مستوى موحد.
- لا يوجد `comments.php`، مع أن القالب يعرض عدادات التعليقات ويعتمد Cusdis خارجيًا؛ يجب تحديد هل التعليقات الأصلية مدعومة أم أن Cusdis تكامل اختياري مستقل.
- تعيين تعطيل خريطة WordPress Sitemap من القالب (`inc/setup.php:218`) قرار بنيوي/SEO يجب ألا يكون مفتوحًا بهذه الصورة داخل Theme؛ الأفضل نقله إلى إضافة أو جعله يتطلب سببًا واضحًا ويتحقق من وجود نظام SEO بديل.
- معظم ملفات `inc/` لا تحتوي حارس `ABSPATH`، بينما بعض الأجزاء تحتويه؛ توحيد السلوك مطلوب.

### 4.3 الوصولية والتفاعل — P0/P1

- القائمة الجانبية لا تحدّث `aria-expanded` ولا `aria-controls`، ولا تنقل التركيز إلى اللوحة ولا تعيده إلى زر الفتح، ولا تمنع التركيز من التسرب إلى خلفها.
- طبقة البحث لا تحتوي `role="dialog"` أو `aria-modal`، ولا يوجد focus trap أو حفظ لعنصر التركيز السابق أو إدارة scroll للصفحة.
- زر تبديل النمط يغيّر `htmlElement.className` كاملًا في `assets/src/js/main.js:276-282`؛ هذا قد يمسح أي class تضيفه إضافة أو أداة أخرى. يجب تبديل `dark/light` فقط.
- السلايدر يعمل تلقائيًا دون زر إيقاف/تشغيل، ولا يطبق `prefers-reduced-motion`، ولا يحدد `aria-hidden` للشرائح غير النشطة، وقد تظهر جميع الشرائح لقارئ الشاشة.
- أزرار المشاركة تعتمد على `title` دون `aria-label` واضح، وزر الطباعة يستخدم inline `onclick`.
- الحقول التفاعلية لا تملك دائمًا حالات خطأ أو رسائل مرتبطة بـ`aria-describedby`، خصوصًا نموذج الاشتراك.
- الاعتماد على hover لإظهار بعض عناصر الهيدر والسلايدر يضعف الاستخدام باللمس ولوحة المفاتيح.

### 4.4 الأمان والخصوصية — P1

- تحميل Prism من CDN وCusdis وUmami وGoogle Analytics يخلق اعتمادًا على أطراف خارجية، ويؤثر على الخصوصية وCSP ووقت العرض. لا توجد SRI hashes أو سياسة واضحة للموارد الخارجية.
- Google Analytics يُحقن مباشرة عند إدخال المعرف، دون طبقة موافقة/consent. يجب تحديد متطلبات الخصوصية قبل التفعيل.
- `inc/logging.php` يكتب داخل `uploads/opentik-logs` وقد يكون قابلًا للوصول عبر الويب، ولا يملك تدويرًا أو حماية أو تنظيفًا للبيانات. كما أن `shell_exec()` لكل سجل ليس مسارًا موثوقًا لخدمة logging غير متزامنة.
- `opentik_log()` غير مستخدمة في الكود الحالي، لذا فهي تعقيد وصيانة بلا فائدة تشغيلية إلى أن تُربط بمسارات أخطاء حقيقية.
- بعض sanitizers تستخدم `sanitize_text_field` لقيم enum بدل whitelist صريحة. هذا لا يسبب ثغرة مباشرة في معظم المواضع، لكنه يسمح بقيم غير معروفة ويزيد حالات الانحراف.
- `opentik_the_excerpt()` يطبع الملخص دون `wp_kses_post()` في السطر 51 من `inc/template-tags.php`. ينبغي توحيد سياسة إخراج المحتوى، خصوصًا عند بناء الملخص من `get_the_content()`.

### 4.5 الأداء والكاش — P1

- الصفحة الرئيسية تشغّل Query للسلايدر ثم Query القائمة الرئيسية؛ صفحة المقال تضيف Query للمختارات والرائج والتصنيفات والوسوم، والفوتر قد يشغل Query رائجًا آخر.
- لا يوجد transient/object cache أو تجميع واضح للبيانات المشتركة بين الهيدر والشريط الجانبي والفوتر.
- السلايدر يستخدم صورة fallback من `picsum.photos`، ما يضيف طلبًا خارجيًا غير ثابت عند غياب الصورة.
- CSS يحتوي عددًا كبيرًا من القيم الصلبة و`!important` وutility classes عشوائية؛ الناتج النهائي قرابة 98KB، وهو مقبول مبدئيًا لكنه قابل للتقليل بعد إزالة التكرار.
- الخلفية المتحركة المستمرة و`backdrop-filter` والـ blur قد تكون مكلفة على الأجهزة الضعيفة، ولا يوجد مسار واضح للأجهزة منخفضة القدرة.
- عداد الساعة يحدث كل ثانية حتى لو لم تكن القيمة مفيدة للمحتوى، ولا يراعي locale/منطقة WordPress الزمنية بنفس طريقة PHP بالضرورة.

### 4.6 SEO وصحة المحتوى — P1

- لا يوجد JSON-LD للمقال أو الموقع، ولا canonical صريح، ولا Open Graph/Twitter Cards.
- لا يوجد وصف منظم للمقال يتضمن المؤلف وتاريخ التحديث والموضوع، والبطاقات تعرض تاريخ النشر فقط.
- استخدام `date()` في الفوتر بدل تاريخ WordPress المحلي غير متسق مع إعداد المنطقة الزمنية.
- الشريط يستخدم صور background، فلا توجد `alt` دلالية للصورة عند كونها جزءًا من المحتوى.
- لا يوجد author archive أو taxonomy-specific templates، ما يجعل الاعتماد على القوالب العامة أكبر من اللازم.
- لا يوجد نظام واضح للتوافق مع Yoast/Rank Math؛ الأفضل أن يقدم القالب الأساسيات فقط ويتجنب التنافس مع الإضافات.

### 4.7 قابلية الصيانة والتوثيق — P1/P2

- `inc/setup.php` يجمع setup وCustomizer وanalytics وsanitizers في ملف واحد كبير، بينما `footer.php` يحمل منطق builder واستعلامات وhelper functions وعرض HTML في ملف واحد.
- 61 إعدادًا في Customizer مع تسميات وقيم افتراضية موزعة، وبعض الخيارات تستخدم sanitization عامة بدل registries مركزية.
- `opentik_get_grid_class()` معرفة في `footer.php` بدل طبقة مساعدة، ولا تحيط بها `function_exists()` مثل helper المحاذاة.
- تكرار منطق الهوية والعنوان واللون وحساب brightness في الهيدر والفوتر؛ أي تعديل يحتاج أكثر من موضع وقد ينتج عنه عدم اتساق.
- أسماء الفئات تمزج بين مفاهيم عربية/إنجليزية وTailwind utilities وCSS components دون قاموس تسمية موثق.
- `style.css` يحمل فقط metadata تقريبًا، بينما قواعد التصميم كلها في CSS المولد؛ هذا صحيح تقنيًا مع البناء لكنه يحتاج توثيقًا واضحًا لآلية التطوير والنشر.
- لا توجد اختبارات وحدات PHP، اختبارات قوالب، اختبارات JavaScript، أو اختبار قبول للوحة المفاتيح.

## 5. تقييم نظام التصميم

### 5.1 ما هو موجود

- متغيرات ألوان أساسية للنمطين في `assets/src/css/style.css`: خلفية، بطاقة، حدود، نص رئيسي، نص ثانوي، accent، ظلال.
- أنماط مكونات واضحة بصريًا: card، header، footer، overlay، mobile drawer، pagination، code block، hero.
- أحجام وتحولات responsive مع نقاط `md` و`lg`، وواجهة RTL مستمرة.

### 5.2 ما ينقص

| الفئة | الملاحظة | المعالجة |
|---|---|---|
| الألوان | وجود قيم hex/rgba كثيرة داخل المكونات | نقل الألوان الدلالية إلى tokens، والسماح بالـ hex فقط داخل ملف tokens |
| المسافات | utility values كثيرة وقيم arbitrary | اعتماد scale موحد للمسافات وربط المكونات به |
| الخطوط | لا يوجد قرار موثق للخط العربي أو fallback | تعريف typography scale وأوزان وحدود line-height |
| الحدود والزوايا | `rounded-xl/2xl/3xl` مستخدمة بلا قواعد مكونية | تعريف radius tokens حسب نوع المكون |
| الحركة | انتقالات كثيرة بلا سياسة reduced motion | tokens للحركة وإيقافها عند تفضيل المستخدم |
| الحالات | hover موجود بكثرة، بينما focus/disabled/error ناقصة | توثيق جميع states لكل مكون |
| الأسماء | أسماء مثل `brand-capsule` و`post-card` مع utilities مباشرة | اعتماد طبقة مكونات بسيطة وأسماء مستقرة |
| التوثيق | لا يوجد كتالوج للمكونات | إضافة `docs/design-system.md` أو Storybook-like pages داخل التوثيق |

### 5.3 المكونات التي تحتاج توثيقًا أولًا

2. Mobile drawer.
3. Search dialog.
4. Post card في variants: grid/list/masonry.
5. Single post hero.

لكل مكون يجب توثيق: الغرض، variants، الحالات، keyboard behavior، ARIA، القيود responsive، والـ tokens المستخدمة.

## 6. المعالجة المقترحة وإعادة الهيكلة

### المرحلة 0 — تثبيت خط الأساس

- اعتماد هذا التقرير كخط أساس، وتحديث `PROJECT_MAP.md` ليصف التنفيذ الحالي لا المستهدف.
- إنشاء `specs/001-theme-hardening/spec.md` و`plan.md` و`tasks.md` قبل التعديلات الواسعة.
- تحديد قرار واضح: هل النشرة البريدية، Cusdis، Analytics، والسلوك الديناميكي مكونات أساسية أم تكاملات اختيارية.
- تثبيت معيار قبول: PHP 7.4 إن كان مطلوبًا فعلًا، أو رفع الحد الأدنى إلى نسخة مدعومة فعليًا بعد قرار النشر.

### المرحلة 1 — الأساس WordPress والوظائف الحرجة

- إضافة `wp_body_open()` بعد فتح body.
- نقل إعدادات التسجيل والتكاملات إلى ملفات مستقلة، وإضافة guards موحدة.
- بناء registry مركزي لقيم Customizer مع whitelist وdefaults و`transport` واضح.
- إزالة أو ربط newsletter بتكامل حقيقي. لا نجاح وهمي.
- تحويل `onclick` إلى event listener، وإضافة `aria-label` و`aria-expanded` و`aria-controls`.
- فصل خيار sitemap عن القالب أو جعله تكاملًا اختياريًا غير افتراضي.

### المرحلة 3 — الوصولية والتفاعل

- تنفيذ focus trap واستعادة التركيز للـ drawer والبحث.

- إضافة `loading="lazy"` حيث يناسب، و`fetchpriority="high"` للصورة البطلة فقط، واختبار Core Web Vitals فعليًا.

## 9. تطبيق Impeccable ونتيجة الجولة الأولى

تم تثبيت Impeccable محليًا تحت `.agents/skills/impeccable/`، وتهيئة detector لقراءة ملفات `.php` كقوالب HTML عبر `.impeccable/config.json`. كما أُنشئت ملفات السياق:

- `PRODUCT.md`: حدود المنتج، المستخدمون المستنتجون، القيود، والتكاملات غير المؤكدة.
- `DESIGN.md`: نظام الألوان، الكتابة، المسافات، المكونات، وقواعد منع الانحراف البصري.
- `.impeccable/design.json`: قواعد العمق والحركة والانحرافات المعروفة.

### الفحص قبل المعالجة

كشف detector الرسمي 12 تنبيهًا مباشرًا في CSS/JS:

- حد accent جانبي بسماكة 4px في عناوين الوحدات والمقال.
- استخدام Inter كخط عام.
- ستة مواضع تقريبًا لـ bounce/elastic easing.
- انتقال `width` في underline، وهو تغيير layout غير ضروري.
- حالتان لنص `slate-900` فوق الأصفر.

### ما عولج في الجولة الأولى

- استبدال Inter مؤقتًا بـ Tahoma/Segoe UI المتاحين محليًا إلى أن يُعتمد خط عربي نهائي.
- تحويل accent الجانبي إلى accent سفلي دقيق.
- استبدال easing المطاطي بـ ease-out ثابت.
- تحويل underline إلى `transform: scaleX()` بدل انتقال `width`.
- إضافة focus-visible موحد وأهداف لمس لا تقل عن 44px.
- إضافة `prefers-reduced-motion` وتعطيل autoplay للسلايدر عند طلب تقليل الحركة.
- إضافة `wp_body_open()` و`aria-expanded`/`aria-controls` للقائمة، وإدارة `aria-hidden` والتركيز للـ drawer/search.
- إيقاف رسالة نجاح النشرة الوهمية؛ تظهر الآن رسالة تجهيز ما لم يوجد endpoint معلن.

### نتيجة الفحص بعد المعالجة

اختفت تنبيهات side-tab وInter وbounce وlayout-transition. بقيت تنبيهات advisory حول ألوان وأحجام موجودة في CSS/Prism وبعض utility classes، إضافة إلى تحذيرات detector عن الألوان الداكنة فوق الأصفر في مواضع أخرى؛ هذه تحتاج قرار token موحدًا لا استبدالًا آليًا عشوائيًا.

هذه الجولة ليست اعتمادًا نهائيًا للوصولية: يلزم تشغيل WordPress حي واختبار متصفح للـ focus trap، السلايدر، قارئ الشاشة، التباين الفعلي، وحالات الخطأ.
